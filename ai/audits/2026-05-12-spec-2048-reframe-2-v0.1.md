## Confirmed claims

The following were positively verified by reading the canonical sources and re-frame2 references:

- **§3.3** Two starting tiles — verified: `this.startTiles = 2` in `game_manager.js`.
- **§3.4** P(2) = 0.9, P(4) = 0.1 — verified: `Math.random() < 0.9 ? 2 : 4` in `game_manager.js`.
- **§3.4** One spawn per successful move — verified: `if (moved) { this.addRandomTile(); ... }`.
- **§3.5** `[2 2 2 2] → [4 4 _ _]` (not `[8 _ _ _]`) — verified: enforced canonically via `!next.mergedFrom` guard on the produced tile, and reset of `mergedFrom = null` in `prepareTiles` only between moves.
- **§3.6** Score increment by produced-tile value — verified: `this.score += merged.value;` in `game_manager.js`.
- **§3.7** Win condition triggers at 2048 — verified: `if (merged.value === 2048) self.won = true;`.
- **§3.9** Continue-after-win semantics — verified: canonical `isGameTerminated()` returns `this.over || (this.won && !this.keepPlaying)`. After `keepPlaying = true`, subsequent `self.won = true` re-assignments are observationally idempotent. Spec's "MUST NOT re-fire `:won`" is the correct port to a phase-FSM model.
- **§3.8 (substantive correctness)** Lose condition — verified: canonical `movesAvailable()` returns `cellsAvailable() || tileMatchesAvailable()`; lose iff neither. The spec captures this (with verbose phrasing; see C-03).
- **SA-3 attribution in §5.2** — verified: SA-3 in re-frame2's `SPEC-AUTHORING.md` does require every wire-shape to be schematised in `Spec-Schemas.md`. (Note: re-frame2's own `010-Schemas.md` describes `:spec` metadata as optional — there is a real tension in the upstream spec between SA-3 and 010-Schemas. That tension is upstream's problem, not this spec's; A-02 stands as written.)

## Auditor's overall read

This is a strong v0.1. The spec is genuinely readable end-to-end without consulting re-frame v1 source (SA-2 ✓). Game mechanics in §3 are essentially correct against the canonical Cirulli source — I expected to find more drift here and didn't. The decisions log §12 is disciplined: every open question has either an operator decision or an explicit mayor-default flag, which is what SA-4 demands. The architecture grammar (§4) hits the major re-frame2 surfaces (events, effects, subs, FSM) with sensible ids. I'd rate it ~85% ready.

The three blockers are real but cheap to fix. A-01 (clojure.spec syntax leaking into a Malli spec) is a copy-paste mistake. A-02 (only 6 of ~17 wire shapes are schematised) is the biggest gap — SA-3 is unambiguous about this and the missing schemas are exactly the shapes an implementing agent needs to validate its event handlers. A-03 (palette ramp deferred to a yet-to-be-created EDN file) is a textbook SA-4 violation: "we'll figure out the colours later" is the indefinite-later question the meta-spec was written to prohibit.

The defects cluster around three themes. (1) The animation/input-gate contract (§6.3 + §5.1 + §4.4) is under-specified — there's a busy flag with no shape, no event to clear it, and a sub-state machine implied but not drawn. An implementer will have to invent this and the resulting code will diverge from any future amendment. (2) The FSM diagram (§4.8) shows only the happy path; `:game/new`-from-anywhere and `:continuing → :over` edges are missing, which directly contradicts §4.4. (3) The `:rng-seed` is in app-db but the threading model is invisible — §9.4's property tests cannot be written without it.

Recommendation: fix the three blockers and B-01..B-08 inline, leave B-09..B-14 for one more operator pass if time-boxed, and the nits can ride. After A-01..A-03 and B-04, B-07, B-08, B-10 are addressed, I'd be comfortable dispatching this to an implementing agent.
